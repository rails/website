<p>In this episode of <em>On Rails</em>, Robby is joined by <a href='https://www.linkedin.com/in/ryanstawarz/'>Ryan Stawarz</a> and <a href='https://www.linkedin.com/in/rubyprogramming'>Austin Story</a> from <a href='https://engineering.doximity.com/'>Doximity</a>, where Ruby on Rails has powered the core of their platform for over 15 years. The trio digs into how a single <a href='https://rubyonrails.org/'>Rails</a> monolith has evolved to support 100+ engineers and a mobile-first experience for millions of healthcare professionals. From front-end framework migrations to API architecture, they explore the real-world decisions required to keep a large Rails app resilient and fast-moving.</p><p>Ryan and Austin walk us through the team’s adoption of <a href='https://graphql.org/'>GraphQL</a>, what led them to introduce <a href='https://www.apollographql.com/docs/federation/'>GraphQL Federation</a>, and how they balance speed with reliability when scaling APIs across domains. They talk about the tradeoffs of maintaining both GraphQL and REST, and how Doximity avoids N+1 query pitfalls using <a href='https://github.com/exAspArk/batch-loader'>BatchLoader</a>. The conversation also touches on the evolution of their front-end—from Backbone to <a href='https://vuejs.org/'>Vue.js</a>—and why Rails’ flexibility still gives them an edge.</p><p>Throughout the episode, they share pragmatic insights into debugging at scale, managing one-off data migrations, and determining when a service should live inside or outside the monolith. They also reflect on their use of tools like <a href='https://github.com/Shopify/packwerk'>Packwerk</a>, <a href='https://anycable.io/'>AnyCable</a>, and <a href='https://github.com/departurerb/departure'>Departure</a>, and how a culture of trust, documentation, and lightweight planning helps Doximity move fast without breaking things.</p><p><b>🧰 Tools &amp; Libraries Mentioned</b></p><p>- <a href='https://rubyonrails.org/'>Ruby on Rails</a> – The web framework powering Doximity’s monolith and many of their services.  </p><p>- <a href='https://graphql-ruby.org/'>GraphQL-Ruby</a> – Ruby gem for building GraphQL APIs in Rails.  </p><p>- <a href='https://github.com/exAspArk/batch-loader'>BatchLoader</a>– Helps reduce N+1 queries in GraphQL.  </p><p>- <a href='https://vuejs.org/'>Vue.js</a> – Their chosen frontend framework for building single-page applications.  </p><p>- <a href='https://github.com/Shopify/packwerk'>Packwerk</a> – Helps enforce modular boundaries in their Rails monolith.  </p><p>- <a href='https://github.com/departurerb/departure'>Departure</a> – Used for safe database migrations on large datasets.  </p><p>- <a href='https://github.com/rails/thor'>Thor</a> – Used to run one-off CLI scripts with easier testability.  </p><p>- <a href='https://github.com/doximity/rake_ui'>rake-ui</a> – Internal tool for triggering Rake tasks via a web UI.  </p><p>- <a href='https://anycable.io/'>AnyCable</a> – Go-based replacement for ActionCable to support realtime features at scale.  </p><p>- <a href='https://www.docker.com/'>Docker</a> – Powers consistent local dev and containerized environments.  </p><p>- <a href='https://firebase.google.com/'>Firebase</a> – Used for push notifications in mobile apps.  </p><p><br/></p><p><br/></p>
